# Передача проекта заказчику

## Какие пакеты передавать

Скрипт `scripts/create_release_bundles.py` всегда формирует архив исходников
текущей версии и, при передаче `--native-package`, добавляет нативный
CPack-пакет. Windows- и evidence-архивы создаются только тогда, когда
`release/VERIFIED_WINDOWS_BUILD.json` подтверждает текущую версию продукта
и схему отчёта, а проверенный EXE доступен:

1. `*-windows-x64.zip` — готовый инструмент для Windows x64: проверенный EXE,
   документация, примеры и импортёр Ghidra.
2. `*-source.zip` — чистые исходники, CMake, тесты, CI и документация для
   дальнейшей разработки.
3. `*-evidence.zip` — доказательная база Windows-проверки: итоговые отчёты,
   машинные результаты и четыре эталонных динамических сценария.

Файл `SHA256SUMS.txt` содержит контрольные суммы созданных архивов.
Версионная копия сохраняется как `SHA256SUMS-<version>.txt`.
Подтверждённые quality gates перечислены в
`release/RELEASE_STATUS_1.0.0_RU.md`. Файл `release/RELEASE_STATUS_RU.md`
сохранён как исторический паспорт предыдущей ревизии `rc1`.

Готовый CPack-пакет текущей операционной системы можно добавить командой:

```sh
python3 scripts/create_release_bundles.py \
  --native-package build/release/eh-unwind-analyzer-1.0.0-<System>-<Processor>.zip
```

Для финальной Windows-поставки используется строгий режим:

```sh
python3 scripts/create_release_bundles.py --require-windows
```

Команда завершится ошибкой, если проверенный Windows EXE или его manifest
не соответствуют текущей версии. Это исключает случайную выдачу старого
бинарника за новый релиз.

Манифест от июня 2026 года описывает схему `1.1.0`, тогда как текущие исходники
используют `1.3.0`. До обновления манифеста и подтверждённого EXE обычный
запуск создаёт только архив исходников. Результаты проверки текущего кода
описаны в [`GITHUB_PREPARATION_RU.md`](GITHUB_PREPARATION_RU.md).

## Что не входит в пакет заказчика

- локальные каталоги `build/`;
- кэши Python и служебные файлы macOS;
- полный корпус сторонних PE-файлов;
- промежуточные и устаревшие Windows-бинарники;
- временные журналы и результаты локальных экспериментов.

Полный корпус хранится отдельно и нужен только для повторной инженерной
валидации. Его не следует включать в обычный релиз без отдельной проверки
лицензий источников.

## Проверка перед передачей

```sh
cmake --preset release
cmake --build --preset release
ctest --preset release

cmake --preset sanitize
cmake --build --preset sanitize
ctest --preset sanitize

python3 scripts/create_release_bundles.py --require-windows
```

На Windows дополнительно выполняются MSVC/MinGW CTest и
`tests\run_dynamic_smoke_windows.bat`.

## Ограничения

- статический анализ PE32+ AMD64 работает на Windows, Linux и macOS;
- динамический режим работает только на Windows x64;
- динамический запуск предназначен для EXE; DLL/PYD требуют отдельного
  процесса-хоста;
- неизвестные файлы следует запускать только в изолированной Windows VM;
- для проверенной версии динамического режима рекомендуется использовать
  ASCII-пути.
